Files-DB

A folder is the record.
Reading it should cost nothing.

Quanta keeps every node in its own directory, with its own data.json. That is wonderful to version, to diff and to grep — and it used to mean an exec(find) and a json_decode every time a page needed a node.

Files-DB is a PHP extension written in Rust, plus a daemon called qdbd. The daemon reads the tree once and publishes it into shared memory; every PHP worker maps that memory read-only and answers a lookup with a hash probe. The files never stop being the truth.

  • 16–279× faster than reading and decoding the file
  • 0 syscalls on a read
  • 0 data migration — it is still just folders
  • Falls back to the filesystem if the daemon is gone

Watch it happen

Three moments in the life of one node — first-post. Press play, or step through them yourself.

  1. One daemon, one root

    qdbd is told nothing except where the data lives. Everything else — the socket, the lock directory, the segment path — is derived from that one path, so the extension, the daemon and qdbstat all find each other without a registry.

  2. Watch first, look second

    Stale segments are deleted, the epoch number is bumped so it is never reused, and the inotify watches go on before the scan starts. Reading first would miss a node created halfway through — and could catch a file mid-write, at zero bytes.

  3. Read the whole tree, once

    Every directory becomes a record: its name, its father, its children, its symlinks. Every data.json and data_<lang>.json is parsed — which is also how corruption is found early rather than on a Tuesday afternoon.

  4. Keep the decoded form, not just the bytes

    Since the daemon has parsed the document anyway, it stores the result: a pre-decoded image laid out so PHP can adopt it as-is. This is where the 27× on a small document and the 279× on a big one come from.

  5. Publish the segment

    The whole index is written into one file on tmpfs: a hash slot array pointing into an arena of records. qdbd is the only process that ever writes it, which is why readers need no lock and can never see a half-written record.

  6. Only now, open the door

    The socket is bound last and the coherence flag is raised, so a successful connect always implies "already serving". From here the daemon sits in a poll loop on inotify and client writes, with a one-second heartbeat.

  1. The worker maps the segment

    On its first call the process opens the active segment and mmaps it PROT_READ. That is the entire setup: no connection, no handshake, no session. The daemon is not in the read path and cannot slow it down.

  2. Is the index trustworthy?

    A read first glances at the control arena: the coherence flag set, and a heartbeat less than five seconds old. If either fails, everything below is skipped and Quanta's original filesystem code runs instead — the same answers, the old speed.

  3. The name is the address

    Node names are globally unique in Quanta, so the name hashes straight to a slot: sixteen bits become a tag, the rest an index. Where this used to be an exec(find) across the tree, it is now one multiplication and a mask.

  4. One probe

    Slot 5's tag matches, so the offset is followed into the arena and the full hash and the full name are compared. A tag collision therefore just continues the probe; it can never return the wrong node. A torn slot can only produce a miss, and a miss falls back.

  5. The document is already decoded

    The record carries the image, so PHP walks it directly into values: no open, no read, no tokenizing, no UTF-8 revalidation. With zero-copy on, the strings are not even copied — the zvals point into the mapping, which is why a 205 KB document costs the same as a small one.

  6. Exactly what json_decode would have returned

    Same array, same types, same nesting — the call site does not know or care where it came from. That is the whole trick: the fast path had to be invisible, or it could not have been dropped underneath code that already worked.

  7. And when the node isn't there

    Under a coherent daemon a miss is an authoritative absence: the answer is null without touching the disk at all. Quanta asks about names that do not exist constantly — every field it is not sure about — and each of those used to be a walk of the tree.

  1. Take the lock, read the document

    update() holds a per-node flock across the whole callback, so the read-modify-write cannot interleave with another request doing the same thing. Two editors saving at once produce two saves, not one lost one.

  2. Disk first — always

    The new document goes to a temporary file, is fsynced, and is moved into place with an atomic rename. The file is the source of truth, so it is what has to survive the power cut; shared memory is only ever a derived copy.

  3. Tell the daemon

    Only after the bytes are safely on disk does the worker send a short frame over the unix socket. Its own inotify would have caught the change anyway — the socket is what makes the timing predictable instead of eventual.

  4. A new record, then a pointer flip

    The daemon re-reads the file, bumps the node's generation — the cache key every worker checks — appends a fresh record to the arena, and only then points the slot at it. Readers see the old record or the new one, never a mixture. The old bytes become garbage, reclaimed at the next compaction.

  5. Acknowledge after publishing

    This ordering is the point of the whole channel. When update() returns, the change is already visible in shared memory, so the next request — in a different process, on a different core — reads the new title. No polling, no TTL, no "eventually".

  6. What if the daemon died mid-write?

    The write is already on disk, so nothing is lost. The worker waits 250 ms for an ack it will not get, marks the index incoherent, and everyone quietly goes back to reading files. When qdbd comes back it rescans and republishes, and the fast path resumes.

Past write_ack_timeout_ms (250 ms) coherence is poisoned and every worker goes back to walking the tree, exactly as Quanta did before the extension existed. Slower. Never wrong.

What that buys, and what it costs

The design is chosen so that the interesting failure modes are boring ones.

Nothing to migrate

Everything in shared memory is derived from the files and can be rebuilt at any moment. Delete the segment, restart the daemon, and you are back where you were.

Never load-bearing

Every call site keeps its original filesystem code as a fallback, and a test suite runs the same assertions with the daemon, without it, and without the extension loaded at all.

Read your own writes

The daemon acks only after the change is published, so a write in one process is visible to the next request in another. No cache TTL to tune.

A miss is an answer

With a coherent index, "no such node" is returned without a single syscall — which matters, because asking about names that do not exist is something a CMS does all day.

Writes are atomic

Lock, temp file, fsync, rename. A crash leaves the old document or the new one, and a concurrent reader never sees a half-written file.

Per-pod, not per-cluster

The segment and the counters live in the pod's own memory. qdbstat reports the pod it runs in; there is deliberately no aggregated view.

Measured, not estimated

One Node::loadJSON-equivalent read, 20 000 iterations, against a live daemon. The last column is the default configuration.
