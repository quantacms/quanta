quanta_db — before / after

Quanta stores every node as a folder with JSON documents. This page shows what the quanta_db Rust extension changes versus the legacy access patterns — animated, with the real measured numbers.

1 · Finding a node by name

Node names are globally unique, but nothing recorded where a folder lives. Before: a cold lookup shells out to find and walks the whole docroot. After: one lookup in a derived SQLite index (rebuildable any time — files stay the source of truth).

BEFORE exec("find /docroot/ -type d -name booking-1523 …")
0µs
AFTER QuantaDb::path("booking-1523")
0µs

Numbers are real (409-node bench tree, in-container: 10,964 µs vs 6.2 µs — ×1,777). The animation is not to scale: drawn to scale, the index lookup would finish in ~2 ms of this 4-second sweep. The production tree is larger, so the real gap is bigger.

2 · Writing a document

Before: fopen('data.json','w+') truncates the file first, then writes — no lock, no fsync. Any reader arriving mid-write sees an empty or half-written document. After: the extension writes a temp file, fsyncs, then atomically rename()s it into place under a per-node lock — readers always see a complete document (old or new, never torn).

BEFOREfopen('w+') + fwrite
db/booking-1523/data.json⚠ truncated
CONCURRENT READER
idle
AFTERQuantaDb::put — tmp + fsync + rename + flock
db/booking-1523/data.json⇄ rename()
db/booking-1523/.data.json.tmpfsync ✓
CONCURRENT READER
idle

This is the deliberate trade-off: legacy's unlocked write is ~30 µs, the safe write costs ~1 ms. CMS traffic is overwhelmingly reads.
